# **UNIT 1 – SOFTWARE PROCESS AND AGILE DEVELOPMENT**

## **Part A – 2-Mark Answers**

**1. Define Software Engineering. What is Software Crisis?**

- **Software Engineering:** Software Engineering is the systematic application of engineering principles, methods and tools to develop, operate, test and maintain software.
- **Software Crisis:** Software Crisis refers to problems in software development such as high cost, late delivery, poor quality, complexity and difficulty in maintenance.

**2. Waterfall Model vs Incremental Model**

| Waterfall Model                           | Incremental Model                        |
| ----------------------------------------- | ---------------------------------------- |
| Development follows a sequential process. | Development occurs in small increments.  |
| Each phase is completed before the next.  | Each increment adds new functionality.   |
| Changes are difficult to make later.      | Changes can be handled more easily.      |
| Working software is delivered at the end. | Working software is delivered regularly. |

**3. What are the Agile Manifesto principles?**

The Agile Manifesto contains four core values:

1. Individuals and interactions over processes and tools.
2. Working software over comprehensive documentation.
3. Customer collaboration over contract negotiation.
4. Responding to change over following a plan.

It also contains 12 supporting principles, including early delivery, continuous customer satisfaction, teamwork, simplicity and regular improvement.

**4. What are the 12 XP practices?**

Extreme Programming (XP) uses these 12 practices:

1. Planning game
2. Small releases
3. System metaphor
4. Simple design
5. Testing
6. Refactoring
7. Pair programming
8. Collective ownership
9. Continuous integration
10. 40-hour week
11. On-site customer
12. Coding standards

### **1. Explain Waterfall, Incremental, Spiral and Prototyping Models with diagrams, advantages, disadvantages and applications.**

**Introduction**

A Software Development Life Cycle (SDLC) model describes the steps followed to develop software. It provides a systematic approach for planning, designing, coding, testing and maintaining software.

**1. Waterfall Model**

The Waterfall Model is a traditional software development model. Each phase must be completed before moving to the next phase.

[Software Development Methodologies: A Deep Dive into the Waterfall Model: Part 2 📈 – The Rails Drop](https://images.openai.com/static-rsc-4/hSOHGxTERc8TE1m3O3YTfGLUwllOHKeAVO4wyKGVZr4wq53YIM6Mg8ACd-B-RYJfp8-0Iom-c0l5Fhcm5Wj82QC1k1-WBbBMdSccUmfnxbBR82JoCEPFEQuS68jTqfmH9C14lRcrjPqpYITii86uA35L06k1BzvzC0Q3-q77OCA?purpose=inline)

[railsdrop.com](https://railsdrop.com/2025/07/18/software-development-methodologies-a-deep-dive-into-the-waterfall-model-part-2/?utm_source=chatgpt.com)

**Phases:**

1. Requirement Analysis – Collect and analyse user requirements.
2. System Design – Prepare architecture, database and interface design.
3. Implementation – Convert the design into program code.
4. Testing – Identify and correct errors.
5. Deployment – Install the software for users.
6. Maintenance – Fix bugs and improve the system.

**Advantages:**

- Simple and easy to understand.
- Clearly defined phases.
- Easy to manage.
- Suitable for projects with fixed requirements.

**Disadvantages:**

- Difficult to change requirements.
- Testing happens relatively late.
- Working software is available only near the end.
- Not suitable for highly changing projects.

**Applications:** Small payroll systems, basic billing software and projects with stable requirements.

**2. Incremental Model**

The Incremental Model develops software in small parts called increments. Every increment adds new features to the existing system.

**Working:**

1. Collect overall requirements.
2. Divide the system into smaller modules.
3. Design and develop the first increment.
4. Test and deliver it.
5. Develop the next increment.
6. Integrate all increments into the final product.

**Example – College Management System:**

- Increment 1: Student registration.
- Increment 2: Attendance management.
- Increment 3: Fee payment.
- Increment 4: Examination results.

**Advantages:**

- Early delivery of working software.
- Easier testing and debugging.
- Supports changing requirements.
- Reduces initial delivery risk.

**Disadvantages:**

- Requires good planning.
- Integration may become complex.
- Overall architecture must be designed carefully.

**Applications:** E-commerce websites, banking applications and college portals.

**3. Spiral Model**

The Spiral Model combines iterative development with risk analysis. Software is developed through repeated cycles called spirals.

[6 Software Testing Methodologies to Explore](https://images.openai.com/static-rsc-4/k-7phuRev8tHGp6UelhY25AWyWr0Io8zRX6LIM5R6-pCm2L0zoXCU9FmEYw8ZesX07F4I_xwQSYU0bgDuZ9bA-F2WLH2jrBDnIAxQ0JZELllLVM2Op5Um3UTCraUT2JjfibfLR4X9BUsTgmV_5XmiHuICULfn84kuhKaxA4xYJ8?purpose=inline)

**Four main activities:**

1. Planning – Identify objectives, requirements and alternatives.
2. Risk Analysis – Identify risks and find solutions.
3. Engineering – Design, code and test the software.
4. Evaluation – Customer reviews the result and provides feedback.

Each spiral produces an improved version of the software.

**Advantages:**

- Strong risk management.
- Supports changing requirements.
- Suitable for large and complex projects.
- Customer feedback is considered regularly.

**Disadvantages:**

- Expensive to develop.
- Requires risk-analysis experts.
- Difficult to manage.
- Not suitable for small projects.

**Applications:** Aerospace systems, defence software, large banking systems and safety-critical applications.

**4. Prototyping Model**

A prototype is an early working model of the software. It is developed to understand and validate customer requirements.

[A Deep Dive into Prototype Model in Software Engineering | Relia Software](https://images.openai.com/static-rsc-4/VbHUJkFh7ht94EljfSTEBDtAcU82gz0pzjY-LFIAbkTMSnzwXHWb8GwTNQ8xVqsF9GEo5bqR8EPhNU4XtZSQswTQCAkNWKgag7rGgkQYAz6vj1aR1m7aRkQAdlSWa979puNOhVB_8a02nbQZHr16UbnlVrBsPBSpUSfLXBD5YZs?purpose=inline)

**Steps:**

1. Collect initial requirements.
2. Prepare a quick design.
3. Build a prototype.
4. Show it to the customer.
5. Collect feedback.
6. Modify and improve the prototype.
7. Develop and test the final system.

**Advantages:**

- Helps understand unclear requirements.
- Customer involvement is high.
- Reduces misunderstanding.
- Improves user-interface design.

**Disadvantages:**

- Frequent changes may increase cost.
- Users may think the prototype is the final product.
- Poor prototype design may affect the final system.

**Applications:** Online shopping interfaces, mobile applications, booking systems and new product development.

**Comparison**

| Model       | Main Feature           | Best Suitable For        |
| ----------- | ---------------------- | ------------------------ |
| Waterfall   | Sequential development | Fixed requirements       |
| Incremental | Small feature releases | Modular applications     |
| Spiral      | Risk analysis          | Large, high-risk systems |
| Prototyping | Early sample system    | Unclear requirements     |

**Conclusion:** Each SDLC model has its own strengths. The model should be selected based on project size, risk, budget, customer requirements and complexity.

### **2. Explain Agile Process in detail. Compare Agile and Traditional Process.**

**Introduction**

Agile is an iterative and incremental software development approach. It develops software in small cycles and continuously collects customer feedback.

[Agile development process infographic](https://images.openai.com/static-rsc-4/KYrW5bXQXMnhcj8If7K7Dgtp6epLT_zBkiGy3Z1piqhLYX5-GWn-t6hkPK5-FGUgeVWwpEebedJXMRTQY-nnZU3q7O-U3NMhK1ZxnjRKh6gEpTDyktms4IYktDlJ6gI0ZiWlFNdc32eXAretzK7-OaqBwu0o7UJCCZbl12nD16MvXoBX2_XzsuSX44Qoy-96?purpose=inline)

**Agile Process:**

1. Requirement Collection – Understand customer needs.
2. Product Backlog – Prepare a list of features and tasks.
3. Sprint Planning – Select tasks for the current sprint.
4. Design – Prepare the required system design.
5. Development – Developers write the code.
6. Testing – Test the developed features.
7. Sprint Review – Demonstrate the working software.
8. Retrospective – Discuss what went well and what must improve.
9. Next Sprint – Repeat the process until the product is complete.

**Important Agile Roles:**

- Product Owner – Defines requirements and priorities.
- Scrum Master – Helps the team follow Agile practices.
- Development Team – Designs, codes and tests the product.
- Customer – Provides feedback and validates the product.

**Agile Principles:**

- Deliver working software frequently.
- Welcome changing requirements.
- Maintain continuous customer collaboration.
- Encourage face-to-face communication.
- Build projects around motivated individuals.
- Focus on technical excellence.
- Keep the process simple.
- Regularly improve the team's work.

**Example – College Management System**

The team can develop the application in multiple sprints:

- Sprint 1: Login and registration.
- Sprint 2: Student profile.
- Sprint 3: Attendance.
- Sprint 4: Fees and payments.
- Sprint 5: Results and reports.

After each sprint, the college can review the features and suggest changes.

**Agile vs Traditional**

| Agile Process                  | Traditional Process                 |
| ------------------------------ | ----------------------------------- |
| Iterative and incremental      | Usually sequential                  |
| Frequent releases              | Often one major final release       |
| Welcomes changing requirements | Changes may be difficult            |
| Continuous customer feedback   | Customer involvement may be limited |
| Testing occurs throughout      | Testing may occur after development |
| Flexible planning              | More fixed planning                 |
| Suitable for dynamic projects  | Suitable for stable requirements    |

**Advantages of Agile:**

- Faster delivery.
- Better customer satisfaction.
- Early identification of defects.
- Flexible to changes.
- Continuous improvement.

**Disadvantages:**

- Requires active customer involvement.
- Cost and time may be difficult to predict.
- Frequent changes may affect scope.
- Requires experienced team members.

**Conclusion:** Agile improves software quality and customer satisfaction through frequent delivery, teamwork and continuous feedback.

### **3. Explain Extreme Programming (XP) Process with Planning, Design, Coding and Testing phases.**

**Introduction**

Extreme Programming (XP) is an Agile software development methodology. It focuses on high-quality software, frequent releases, customer involvement and continuous testing.

[What Is Agile Project Development?](https://images.openai.com/static-rsc-4/X-15gUn3sF7hlsTCxFsfM8UpYKcOnnYi-c4-OLRG52t-qhqfr24ZTs-kjaHGm-5RYChcIUbb5Y7EvkSZzSDWk_USurLnkfeqLDEFH2xjIcsctdpow7vIeGcNXdPljNX6xbsCtUZQxBfTq0Q_15xW9Z3qlzP-LclEWFD7azkofu4?purpose=inline)

**XP Process**

**1. Planning Phase**

- Collect customer requirements.
- Prepare user stories.
- Estimate time and effort.
- Prioritise important features.
- Plan small releases.

Example: For an online food ordering application, user stories include login, restaurant search, cart and payment.

**2. Design Phase**

- Select a simple design.
- Identify classes and modules.
- Prepare system architecture.
- Use CRC cards if required.
- Refactor the design when necessary.

XP follows the principle of keeping the design as simple as possible.

**3. Coding Phase**

- Follow coding standards.
- Use pair programming.
- Integrate code continuously.
- Share code ownership.
- Write unit tests.

**Pair Programming:** Two programmers work together at one computer. One writes code while the other reviews it.

**4. Testing Phase**

- Perform unit testing.
- Perform acceptance testing.
- Run automated tests.
- Correct errors immediately.
- Obtain customer feedback.

**12 XP Practices**

1. Planning game
2. Small releases
3. System metaphor
4. Simple design
5. Testing
6. Refactoring
7. Pair programming
8. Collective ownership
9. Continuous integration
10. 40-hour week
11. On-site customer
12. Coding standards

**Advantages:**

- Improves code quality.
- Early defect detection.
- Frequent software releases.
- Strong customer involvement.
- Supports changing requirements.

**Disadvantages:**

- Requires continuous customer participation.
- Pair programming may require more resources.
- Difficult for very large distributed teams.
- Needs disciplined developers.

**Conclusion:** XP improves software development through simple design, frequent testing, teamwork and continuous feedback.

# **UNIT 2 – REQUIREMENTS ANALYSIS AND SPECIFICATION**

## **Part A – 2-Mark Answers**

**1. What is SRS? What are its contents?**

SRS stands for **Software Requirements Specification**. It is a document that describes the complete functional and non-functional requirements of a software system.

**Contents:**

- Introduction
- Purpose and scope
- Overall description
- Functional requirements
- Non-functional requirements
- External interface requirements
- System constraints
- Assumptions and dependencies

**2. Functional vs Non-functional Requirements**

| Functional Requirements        | Non-functional Requirements                      |
| ------------------------------ | ------------------------------------------------ |
| Describe what the system does. | Describe how well the system works.              |
| Define system features.        | Define quality attributes.                       |
| Example: User login.           | Example: Login should complete within 2 seconds. |

**3. Use Case Diagram Symbols**

- Actor – Stick figure representing a user or external system.
- Use Case – Oval representing a function.
- System Boundary – Rectangle showing system scope.
- Association – Line connecting actor and use case.
- Include – Mandatory reusable behaviour.
- Extend – Optional or conditional behaviour.
- Generalization – Inheritance relationship.

**4. Explain DFD Levels 0, 1 and 2.**

- **Level 0:** Context diagram showing the complete system as one process and its external entities.
- **Level 1:** Divides the main process into major sub-processes.
- **Level 2:** Further divides a Level 1 process into detailed sub-processes.

   - Scope
   - Definitions
   - References
2. Overall Description
   - Product perspective
   - User characteristics
   - Operating environment
   - Constraints
3. Functional Requirements
4. Non-functional Requirements
5. External Interface Requirements
6. Database Requirements
7. System Constraints
8. Assumptions and Dependencies

The system is used by students, librarians and administrators.

- Return date

**10. Output Requirements**

- Book availability status.
- Issue details.
- Return confirmation.

- Student borrowing report.

- Only registered users can borrow books.

- Borrowing limits are controlled by library rules.

**12. Assumptions**

**Advantages of SRS**

### **1. Explain Coupling and Cohesion with types, examples and how to achieve low coupling and high cohesion.**

**Introduction**

Coupling and Cohesion are important software design concepts. They help measure the quality and independence of software modules.

### **1. Coupling**

Coupling is the degree of dependency between different modules.

If one module depends heavily on another module, the system has high coupling. If modules work independently, the system has low coupling.

**Types of Coupling**

1. **Content Coupling:** One module directly accesses or modifies the internal data of another module. It is the strongest and least desirable form.
2. **Common Coupling:** Multiple modules share the same global data.
3. **External Coupling:** Modules depend on an externally imposed format, protocol or device interface.
4. **Control Coupling:** One module passes control information that affects another module's behaviour.
5. **Stamp Coupling:** A complete data structure is passed even though only part of it is needed.
6. **Data Coupling:** Modules communicate by passing only the required data through parameters. It is desirable.

**Example:**

In a college portal:

- Student module sends student ID to Attendance module.
- Attendance module uses the ID to retrieve attendance.
- Only necessary data is shared.

This is an example of data coupling.

### **2. Cohesion**

Cohesion is the degree to which the elements inside a module work together to perform a single task.

High cohesion means all functions inside a module are closely related.

**Types of Cohesion**

1. **Coincidental Cohesion:** Unrelated tasks are grouped together.
2. **Logical Cohesion:** Similar types of tasks are grouped together.
3. **Temporal Cohesion:** Tasks that occur at the same time are grouped together.
4. **Procedural Cohesion:** Tasks are grouped because they follow a particular sequence.
5. **Communicational Cohesion:** Tasks operate on the same data.
6. **Sequential Cohesion:** Output from one task becomes input to another task.
7. **Functional Cohesion:** Every element contributes to one specific function. It is the most desirable type.

**Example:**

A Student Registration module contains:

- Validate student details.
- Generate student ID.
- Save student information.

These functions all support student registration, so the module has high functional cohesion.

| Coupling                                | Cohesion                               |
| --------------------------------------- | -------------------------------------- |
| Measures dependency between modules.    | Measures relationship within a module. |
| Focuses on module-to-module connection. | Focuses on internal module elements.   |
| Low coupling is desirable.              | High cohesion is desirable.            |
| Reduces dependency.                     | Improves module responsibility.        |

### **How to Achieve Low Coupling and High Cohesion**

1. Divide the system into independent modules.
2. Give every module one clear responsibility.
3. Avoid unnecessary global variables.
4. Pass only required data between modules.

6. Use well-defined interfaces.
7. Avoid direct access to another module's internal data.

9. Follow object-oriented principles.

**Advantages**

- Easier maintenance.
- Better reusability.
- Easier testing.
- Reduced complexity.
- Improved software quality.

**Conclusion:** A good software design should have low coupling and high cohesion because it improves modularity, reusability, testing and maintenance.

**Important metrics:**

\\[ V(G)=E-N+2P \\]

- N = Number of nodes.

### **3. PERT – Program Evaluation and Review Technique**

PERT is a project scheduling technique used when activity durations are uncertain.

It uses three time estimates:

- Optimistic Time (O): Minimum expected time.
- Most Likely Time (M): Normal expected time.
- Pessimistic Time (P): Maximum expected time.

**Expected Time Formula:**

\\[ TE=\frac{O+4M+P}{6} \\]

**Example Calculation:**

Suppose an activity has:

- O = 2 days
- M = 4 days
- P = 8 days

\\[ TE=\frac{2+4(4)+8}{6} \\]

\\[ TE=\frac{26}{6}=4.33\text{ days} \\]

Expected completion time = **4.33 days**.

**PERT Variance Formula:**

\\[ \sigma^2=\left(\frac{P-O}{6}\right)^2 \\]

\\[ \sigma^2=\left(\frac{8-2}{6}\right)^2=1 \\]

Variance = 1 day².

**Advantages:**

- Handles uncertain activity times.
- Helps estimate project duration.
- Identifies critical activities.

**Disadvantages:**

- Time estimates may be subjective.
- Large networks can become complex.

### **4. CPM – Critical Path Method**

CPM is a project scheduling technique used to identify the longest path of dependent activities in a project network.

The longest path determines the minimum time required to complete the project.

**Example:**

Consider the following activities:

| Activity         | Duration | Dependency |
| ---------------- | -------- | ---------- |
| A – Requirements | 2 days   | None       |
| B – Design       | 3 days   | A          |
| C – Database     | 4 days   | A          |
| D – Coding       | 5 days   | B and C    |
| E – Testing      | 2 days   | D          |

**Network Diagram:**

[PMP Critical Path Method CPM in an easy way - Software engineering](https://images.openai.com/static-rsc-4/0TlGdUa7WIS4mQyPb9SgiSfkZ_IPVstbz8w_Ak59GUnyT53yN9cUZNOnsPVr911ELxXuw0XpeG5N1aguSyznpslPf6Bkh_Cq_XkvacdazcH2-dw-9CMttrbD4M8QCNJ595vjrb8mBZ5ZkB4tyTJNUeSK_hcw--QMF_7mrkf3osw?purpose=inline)

[softwareengineeringfree.blogspot.com](https://softwareengineeringfree.blogspot.com/2019/03/pmp-critical-path-method-cpm-in-easy-way.html?utm_source=chatgpt.com)

**Path Calculation**

Path 1:

A → B → D → E

\\[ 2+3+5+2=12\text{ days} \\]

Path 2:

A → C → D → E

\\[ 2+4+5+2=13\text{ days} \\]

Therefore:

- Critical Path = A → C → D → E
- Project Duration = 13 days.

**Slack**

Slack is the amount of time an activity can be delayed without delaying the overall project.

Activities on the critical path have zero total slack.

**Advantages:**

- Identifies critical activities.
- Helps control project duration.
- Supports resource planning.
- Helps identify schedule delays.

**Disadvantages:**

- Requires accurate activity dependencies.
- Large projects can become complicated.
- Traditional CPM assumes activity durations are known.

### **PERT vs CPM**

| PERT                           | CPM                                                  |
| ------------------------------ | ---------------------------------------------------- |
| Uses three time estimates.     | Usually uses one time estimate.                      |
| Probabilistic.                 | Traditionally deterministic.                         |
| Useful when time is uncertain. | Useful when duration is predictable.                 |
| Focuses on time uncertainty.   | Focuses on critical path and time-cost optimisation. |

**Conclusion:** Project scheduling helps organise project activities. Gantt Charts provide a visual timeline, PERT estimates uncertain durations and CPM identifies the critical path.
